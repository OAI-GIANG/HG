The validator checks declaration shape/reason, not whether an authoritative inventory of the actual mutation proves non-applicability. Thus a caller can misclassify a capability-affecting operation and potentially bypass MAEP-022. Existing `AuthorizationTests.test_exact_authorization_allowed` demonstrates that the false/non-applicable declaration is accepted by the current primitive; this is a concrete code-path finding, not proof of an exploit against a live runtime.
- Resolution status: NOT RESOLVED. No trustworthy runtime classifier or BrainOrchestrator mutation/side-effect boundary exists in the inspected executable source to serve as an authoritative classification source. Adding another caller-supplied boolean, reason, or record would repeat the same trust defect; changing Foundation to reject all non-applicable declarations would also block legitimate Memory data-plane authorization without a runtime replacement. Therefore no speculative code patch was made. Until a trusted classification source is integrated, unknown/uncorroborated applicability must be treated as BLOCKED, and MAEP-022 mandatory runtime enforcement remains NOT_VERIFIED.
- Required reopen conditions: (1) implement/provide the actual BrainOrchestrator execution path; (2) enumerate feature/capability mutation sources and all side-effect adapters; (3) derive applicability from trusted change/mutation metadata or conservatively require MAEP-022 when classification is unknown; (4) make each side-effect boundary re-check the authorization and candidate-bound gate immediately before execution; (5) add end-to-end tests showing both a capability-affecting mutation with a missing/failing gate is denied and a valid gate is required before the side effect; (6) run those tests against the actual runtime and capture candidate-bound evidence in the existing record.
