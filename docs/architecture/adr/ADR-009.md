# ADR-009 — Architecture Economy and Explicit Ownership

- Status: Proposed
- Context: Premature abstractions, duplicate modules and extra services increase failure modes and maintenance cost.
- Decision: Before authorization of any capability-affecting change, apply the mandatory MAEP-022 Capability Overlap & Superiority Gate using existing task/change-plan and ledger records. Add a module only when the completed inventory proves a genuine gap or a necessary trust boundary, and its owner, dependency impact, tests and removal cost are documented. For overlapping capabilities, retain/consolidate around the demonstrably superior safe implementation; deprecate/remove obsolete functionality only with explicit scoped authorization, regression/migration tests and a recovery path. This ADR does not authorize any implementation or deletion by itself.
- Alternatives: Create a service per feature; duplicate logic for convenience; defer ownership decisions.
- Consequences: Smaller initial architecture and stronger ownership; proposals require evidence that an existing module is insufficient.
- Rules: MAEP-022, 028.
- Acceptance evidence: Capability inventory, acyclic dependency graph and ADR for each justified exception. Inventory still required before runtime.
