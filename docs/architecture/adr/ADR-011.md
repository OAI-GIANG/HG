# ADR-011 — Verified loopback service and deterministic release

- Status: Proposed for merge; not yet deployed
- Date: 2026-10-25
- Scope: OAI-GIANG/HG only
- Decision owner: repository owner

## Context

The existing HG runtime is assembled in-process by hg/runtime.py. It already owns task state, re-checks policy at the tool boundary, verifies acceptance evidence, and loads its trust root from the owner-grants manifest pinned to main. At the recorded base, main does not provide a long-running HTTP service or a release format tying installed bytes back to a Git commit.

A previous handoff referred to a Runtime candidate commit and bundle that could not be recovered. That commit was not found in available Git objects or remote refs. This change is a new, isolated implementation against the currently verifiable main baseline, not a reconstruction of the unverified commit.

## Decision

1. Keep hg/runtime.py, TaskStore, ActionGateway, owner-manifest authority, and BrainOrchestrator as the runtime authority. The HTTP layer is a narrow transport adapter, not a second task-state owner.
2. Bind all HTTP listener sockets to IPv4 loopback 127.0.0.1. Require a private operator-generated Bearer token, strict bounded JSON, a loopback Host header, normalized out/ paths, a small endpoint allowlist, and durable idempotency receipts. test.run, url.read and arbitrary/custom tools are not exposed by this HTTP surface.
3. Permit HTTP task submission only when the task carries one mandatory AC-READBACK criterion and at least one fs.write step. The verifier reads the actual written path back from the confined runtime root and compares it with the planned content. Only the actual TaskStore and AcceptanceGate can authorize CLOSED_VERIFIED.
4. Mark a request STARTED in SQLite before performing work. Same-key/different-body is a conflict; same-key/same-body can replay only after a terminal response is durably recorded; an ambiguous prior request remains in doubt and is not replayed automatically.
5. Build releases only from git archive of an explicit commit. Verify the commit/tree, archive digest, file set, Git blob IDs, SHA-256 and byte lengths. On startup and readiness checks, compare the installed release against its manifest and configured release_id.
6. Require strict service configuration, an owner-controlled token file with mode 0600, private state/config paths, and a single-writer OS file lock. Use the canonical source's bounded 300-second trust cache; a stale reload failure blocks rather than reusing old authority. The read-only preflight refuses startup when release integrity or the main-pinned trust root cannot be verified.
7. Use the repository's current CI and PR-only main gate. Release verification runs on Python 3.13 and 3.14 in CI.

## Consequences

- The service remains local to the Android/Termux host. Loopback binding is not a substitute for Android UID or OS isolation.
- Code running as the same Android UID can generally read the token and access the state directory. A bearer token does not protect against a malicious same-UID process.
- The owner manifest on main remains the authority. This ADR does not change trust grants or principal identity.
- SQLite idempotency receipts and existing HG ledgers are durable local state, not cryptographic tamper-proof logs.
- The HTTP API intentionally does not enable arbitrary code execution or URL fetching. Enabling additional tools requires a separate scoped change and negative tests.
- This change does not claim deployment until merge SHA, release manifest, live readiness, smoke test and rollback evidence are recorded.

## Acceptance gates

- Unit and HTTP integration tests cover authentication, Host/loopback, strict body parsing, size limits, path confinement, disabled tools, idempotent replay/conflict/in-doubt, real read-back verification, release determinism/tampering, strict config/token modes and writer locking.
- CI passes on Python 3.13 and 3.14.
- Two builds from the same Git commit have identical archive bytes and release ID.
- The installed release verifies against Git and manifest before startup.
- Deployment remains a separate operational stage with a recorded rollback target.
