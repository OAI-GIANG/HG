# ADR-012 — Single runtime target: runtime.service; policy target MAEP-1.2.0

- Status: Accepted by the repository owner on 2026-10-25 (architecture decision record; changes no code, policy, grant or trust root)
- Date: 2026-10-25
- Scope: OAI-GIANG/HG only
- Decision owner: repository owner

## Context

Two runtime lines exist in OAI-GIANG/HG at the date of this ADR:

- `main` (f2042e1): package `hg/`, entry point `python -B -m hg serve` (ADR-011), trust loaded from `maep/authority/owner-grants.json`. This is the runtime currently operating on the owner's Termux host.
- Branch `stt/maep-v1-20261022` (8dda6d4): `runtime/service.py`, `runtime/composition.py` and `runtime/http_server.py` over `maep/native_authority.py`, `memory/store.py` and `brain/`. Its entry point fails closed (exit 78) because no production factory exists. The trust sources `ApprovedPolicySourceVerifier`, `AuthenticatedSessionResolver` and `ApprovedMemoryRecordVerifier` are interface-only, and the Memory-backed MAEP-022 providers re-enter `NativePolicyEngine.authorize` recursively when composed.

`main` runs MAEP-1.1.0. The branch carries MAEP-1.2.0 (mandatory MAEP-022 capability overlap and superiority gate, MAEP-029/030 prohibitions, MAEP-031). The owner wants HG built from one source with one runtime.

## Decision (architecture)

1. The single target runtime for HG is `runtime.service`.
2. The target policy version for `main` is MAEP-1.2.0.
3. `hg serve` remains the operational runtime until `runtime.service` passes every gate in "Switch gates" below. This ADR does not stop, redeploy or remove `hg serve` or the `hg/` package.
4. Retiring or consolidating `hg/` capabilities happens only through a MAEP-022 gate record (`CONSOLIDATE_KEEP_SUPERIOR` or `DEPRECATE_OBSOLETE`), with inventory, comparison, impact analysis, regression evidence, retirement authorization and a recovery plan.
5. Branch code enters `main` only by pull request with the required CI checks passing and the MAEP-022 evidence required by the policy in force.

## Not decided here (trust authorization)

This ADR is not an owner grant, a trust-root change or policy-approval evidence. In particular:

- Raising `main` to MAEP-1.2.0 needs a separate, explicit owner approval to re-issue `maep/authority/owner-grants.json`, because the trust anchor binds grants to the policy version (`policy_version` in the manifest, `SUPPORTED_POLICY` in `maep/authority/trust_anchor.py`). No agent rebinds grants on its own.
- The policy-approval source, the authenticated-session source and the approved-Memory-record rule for `runtime.service` are owner decisions still to be made. No digital-signature or independent-review mechanism is introduced (MAEP-029/030).

## Switch gates (all required before `runtime.service` replaces `hg serve`)

1. Startup: one production factory selected explicitly through `HG_RUNTIME_FACTORY`, using only owner-approved trust sources; startup fails closed (exit 78) when any source is missing or invalid, and binds IPv4 loopback only.
2. Trust: positive and negative tests for each trust source (missing, wrong type, expired, revoked, out of scope, verifier error, truthy non-boolean result).
3. Recursion: the Memory-backed provider recursion removed without weakening authorization or provenance checks, covered by a regression test.
4. CI: the full suite passes in `unittest (3.13)` and `unittest (3.14)`.
5. End-to-end: on the Termux host, a separate port and state directory, an authorized task runs through authority, Memory and evidence with durable receipts; repeated start/stop leaves state intact.
6. MAEP-022: a gate record approving consolidation of `hg/` with the evidence listed in decision 4.

## Rollback

- Before the switch: nothing changes operationally; `hg serve` keeps running from its verified release.
- At the switch: record the last `hg serve` release ID and its runit configuration as the rollback target. If `runtime.service` fails post-switch checks, stop it and restore `hg serve` from that release.
- No branch or release used as a recovery point is deleted.

## Consequences

- During the transition both runtime lines exist in the repository. One runtime is the target state, not the state at the date of this ADR.
- Work on `runtime.service` continues on its own line; trust changes, policy changes and runtime integration are reviewed as separate pull requests.
